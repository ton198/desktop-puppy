# Windows 端到端与系统验收测试设计

**状态：** 用户已通过
**日期：** 2026-09-28

## 1. 目标

为已经实现的使用统计与尚待验证的 Windows 桌面行为建立可重复、边界清楚的端到端测试：

1. 用真实 WPF 应用和真实统计窗口证明 30 秒自动刷新会读取运行期间新增的 SQLite 使用记录。
2. 用人工触发、真实 Windows 会话/电源通知的验收流程证明锁屏、解锁、睡眠与恢复正确切分使用记录。
3. 把现有纯 DPI/定位策略接入实际桌宠窗口，并在合适的多显示器/DPI 环境验证窗口定位、可见边缘和拓扑变化。

端到端结果必须与单元测试区分。注入模拟事件的测试只证明路由/策略，不得标记成真实 Windows 端到端通过。

## 2. 当前状态与约束

- `tests/DesktopPuppy.UiTests` 已有真实进程启动、UI Automation、测试数据库注入与窗口断言，可承担 30 秒统计刷新用例。
- `UsageStatisticsWindow` 已使用 30 秒 `DispatcherTimer`；现有统计 UI 测试通过手动选择/重开触发刷新，尚未等待这个真实计时周期。
- `SystemEventsSessionPowerEventSource` 已接入 `SystemEvents.SessionSwitch` 和 `SystemEvents.PowerModeChanged`。现有单元测试注入 provider，不验证 Windows 是否实际发送通知。
- `DpiGeometryPolicy`、`PetPlacementPolicy` 有纯函数测试，但 `PetWindow` 当前使用 `WindowStartupLocation="CenterScreen"`，没有原生显示器服务接入或拓扑变化处理。
- 真实锁屏、睡眠、显示设置变化会改变用户的桌面状态；测试不得在无人值守或普通测试运行中自动触发这些动作。
- 各端到端用例必须使用独立临时数据库与应用进程；不得访问或清理用户的生产数据库。
- 不自动解锁、不读取/保存凭据、不自动改显示器拓扑、分辨率、缩放或电源计划。

## 3. 方案决策

### 3.1 统计窗口刷新：可自动运行的长用例

在现有 UI 测试项目增加独立 `LongRunningE2E` 分类。测试启动真实 Desktop Puppy，使用临时数据库，打开统计窗并选定一个不会受到当前活动会话影响的历史日期；先确认基准总时长，再在应用运行期间从第二个 SQLite 连接写入新记录，等待真实 30 秒计时器刷新，并通过 UI Automation 读取变化后的总时长和应用行。

测试不得直接调用 ViewModel 的 `RefreshAsync`、模拟 DispatcherTimer Tick、替换应用时钟或重启统计窗口来达到预期。基准数据和新增数据使用固定的历史本地日期及已结束会话，排除实时前台采样对结果的影响。插入新数据后不再执行会激活统计窗的 UI 操作；测试只做不激活窗口的 UI Automation 读取，确保结果不是由 `Activated` 刷新造成。轮询仅用于等 UI 出现目标数据；最长等待 60 秒，以容纳一个计时周期及桌面调度抖动。

### 3.2 锁屏/睡眠：人工确认的真实系统验收

新增 opt-in 的 Windows 验收入口，不纳入默认测试过滤器。它启动真实应用、隔离数据库和有稳定标题的测试前台窗口，再分步提示操作人员手动锁定/解锁或睡眠/唤醒。应用须运行真实 `SystemEventsSessionPowerEventSource`；验收工具可观察系统通知并在恢复后检查 SQLite 会话边界。

测试不得调用 `LockWorkStation`、`SetSuspendState`、模拟 provider 或注入 app 内部 router 事件。锁屏后的解锁和睡眠后的唤醒均由操作人员完成；验收工具不能处理 Windows 登录界面。用例必须在本地交互桌面、有可见操作提示的情况下运行，并由显式环境开关启用。用户取消或超时应产生清晰的未完成/失败结果，不能伪报通过。

由于 `Windows PowerModes` 提供的是通用 Suspend/Resume 通知，测试只断言“暂停到恢复”的边界，不把系统睡眠与休眠分类当作通过条件。

### 3.3 多显示器/DPI：先接入生产定位，再在合适设备验收

为现有 `MonitorWorkArea`、`DpiGeometryPolicy` 和 `PetPlacementPolicy` 增加真实显示器数据源与 WPF 定位接线。原生枚举、工作区、设备标识与 DPI 信息封装在 Native adapter；WPF 层通过 placement 服务选择/夹取位置，不直接调用 Win32。窗口启动、跨屏 DPI 变化和显示器拓扑变化使用同一坐标转换与可见性规则。显示器消失时按已有设计回退到仍连接的主显示器，并保持桌宠可见。

多显示器验收需显式 opt-in。普通单屏或未达到 DPI 组合要求的环境必须标记为“环境不满足/跳过”，不能记为通过。测试不自行修改 Windows 显示设置，也不自动拔插/禁用显示器；测试人员按验收说明准备至少两个显示器及不同缩放比例，再运行用例。显示器移除场景只由测试人员手动改变拓扑。测试先记录移除前的目标显示器和窗口物理矩形，再按 placement service 的回退规则计算主显示器上的期望矩形并比较；仅验证“窗口还看得见”不够，因为 Windows 可能自行重定位窗口。坐标统一使用物理像素，记录窗口对应的实际 DPI，避免将 WPF DIP 与 Win32 矩形混用。

## 4. 测试层级与运行隔离

| 分类 | 目的 | 默认运行 | 运行环境 |
|---|---|---|---|
| 现有 `Ui` | 快速真实窗口/控件 smoke tests | 保持现状 | 交互式 Windows 桌面 |
| `LongRunningE2E` | 真实 30 秒刷新、跨进程 SQLite 读取 | 不并入普通 `Ui` 过滤；单独运行 | 交互式 Windows 桌面，约 30–60 秒 |
| `WindowsAcceptance` | 真实锁屏/解锁和睡眠/唤醒事件 | 默认不运行；显式开关 + 操作人员步骤 | 本地交互 Windows 会话，允许手动锁定/恢复 |
| `DisplayAcceptance` | 实际多显示器/DPI 与窗口位置 | 默认不运行；检测条件后单独运行 | 至少双屏；混合 DPI 用例需要不同缩放 |
| 单元测试 | Aggregator、路由、几何策略和边界规则 | 保持常规运行 | 不依赖物理设备；不替代以上端到端验收 |

隔离要求：唯一数据库路径、可确定的测试种子、独立桌宠进程、测试结束后关闭被测进程与前台 fixture、删除本次临时目录。环境变量和筛选参数必须写入测试说明及实现计划。

## 5. 端到端用例与逐项目标

每项用例均明确 **Purpose / Coverage / Target effect**；实现时保留在测试源或验收说明中。

### E2E-STAT-01 — 运行中新增数据触发真实 30 秒刷新

- **Purpose：** 证明运行中的统计窗会依靠产品自己的周期计时器刷新，而不是仅靠手动刷新、重开窗口或 ViewModel 单测。
- **Coverage：** 启动 Release WPF 应用；注入隔离 SQLite；加载历史日期基准记录；在统计窗保持打开时由独立连接新增记录；观测总时长和应用列表变化。
- **Target effect：** 最迟在 60 秒内，UI Automation 读到包括新记录在内的正确总时长与应用行；刷新期间宠物和统计窗都保持运行。
- **环境与安全：** 交互桌面；测试分类 `LongRunningE2E`；不访问用户数据库。若 UI Automation 或进程提前退出，明确失败并报告最后一次观察值。

### E2E-POWER-01 — 真实锁屏/解锁切分使用会话

- **Purpose：** 验证 Windows 实际锁定/解锁通知到达应用并切断锁屏期间的使用统计。
- **Coverage：** 活动测试前台窗口、真实锁定和解锁、应用 SQLite 会话数据、解锁后重新采样前台窗口；为验证解锁后的新会话确已落库，在重新采样后再有控制地切换到另一个测试前台窗口以关闭该会话。
- **Target effect：** 锁定前会话在锁定边界附近结束；锁屏区间不记入任何应用使用；解锁并恢复测试前台后产生新会话。时间断言使用通知时间及明确容差。
- **环境与安全：** 仅在本地交互桌面及显式 `WindowsAcceptance` 开关下运行。操作人员手动锁定并解锁；工具不自动锁屏或处理认证。

### E2E-POWER-02 — 真实睡眠/恢复切分使用会话

- **Purpose：** 验证应用实际收到系统 Suspend/Resume 通知，并恢复后续使用采集。
- **Coverage：** 睡眠前活动会话、手动系统睡眠、恢复事件、必要时手动解锁、重新聚焦测试前台及持久化记录；之后有控制地切换前台以关闭恢复后的会话，再检查 SQLite 中睡眠前后两段会话及其边界。
- **Target effect：** 睡眠前会话被关闭，暂停时间不被累计，恢复并重新取得前台后新会话开始；只断言通用 Suspend/Resume，不区分休眠与睡眠。
- **环境与安全：** 仅在显式 `WindowsAcceptance` 流程运行；操作人员确认睡眠和唤醒，测试不调用电源控制 API；超时/中止结果不得算通过。

### E2E-DISPLAY-01 — 混合 DPI 双屏上的真实定位

- **Purpose：** 证明实际 WPF 桌宠定位使用真实显示器工作区和 DPI 转换，而不只是验证纯策略函数。
- **Coverage：** 至少两个连接显示器、不同 DPI 比例、启动位置、移至次显示器、窗口物理矩形、当前显示器工作区与可见边缘规则。
- **Target effect：** 桌宠在目标显示器上正确定位，不越出可见区域；物理尺寸/边缘约束符合 placement policy，跨屏时 DPI 与 WPF 几何协调一致。
- **环境与安全：** 双屏并满足混合 DPI 条件；显式 `DisplayAcceptance`。不修改系统缩放/分辨率；条件不满足时记为跳过并给出原因。

### E2E-DISPLAY-02 — 显示器拓扑变化后仍可找到桌宠

- **Purpose：** 验证桌宠所在显示器消失时，真实应用能使用有效显示器恢复位置。
- **Coverage：** 在次显示器上运行的桌宠、手动移除/禁用该显示器、真实拓扑更新及重新枚举工作区。
- **Target effect：** 桌宠移动/夹取到仍连接的主显示器工作区，物理矩形符合既定回退定位结果、保留规定的可见边缘且应用不崩溃；只因窗口仍可见不能判为通过。
- **环境与安全：** 仅限至少双屏的 `DisplayAcceptance` 流程。测试人员手动改变显示器拓扑；自动化不拔插、禁用设备或更改系统显示设置。

## 6. 生产代码边界

- `DesktopPuppy.UiTests`：新增周期刷新 E2E 和可重用的实时 SQLite/UI Automation 等待辅助方法；默认 `Category=Ui` 不执行慢速用例。
- `tests/DesktopPuppy.WindowsAcceptance`（名称可在计划阶段确认）：承担需要操作人员步骤的锁屏/睡眠验收流程、真实事件监听、数据库断言与分阶段超时；不能复用假 provider 伪装系统端到端。
- `src/DesktopPuppy/Native`：新增显示器拓扑/工作区/DPI 的 Win32 adapter 与接口，集中 P/Invoke。
- `src/DesktopPuppy/Pet/Placement`：新增 production placement service，将 adapter 数据交给已存在的策略；处理启动定位、DPI 变化与拓扑变化。
- `PetWindow` 与 `App`：只负责生命周期/事件转发和 placement service 接线，不包含原生枚举细节。
- 显示器硬件验收使用当前测试进程启动的真实桌宠，通过 UIA/native HWND 矩形读取观察，不通过截图像素颜色猜测窗口位置。

## 7. 失败处理与结果报告

- 30 秒刷新失败要打印起始/目标值、已等待时长、最后 UIA 名称、应用退出状态及被测 DB 路径（不打印 DB 内容或个人标题）。
- 系统验收应区分“尚未完成用户步骤 / 已取消”“未收到真实通知”“通知收到但记录边界错误”和“测试前置条件不满足”；未完成或已取消报告为未完成，条件不足报告为跳过，均不得计作通过。
- 显示器验收记录连接显示器数量、测试运行内的匿名显示器编号、缩放/DPI 和前置条件；不记录完整硬件标识、与验证无关的窗口标题或用户活动数据。
- 所有外部状态等待采用条件轮询和有限超时；退出时关闭测试应用/fixture 并释放事件订阅。

## 8. 验收标准

1. 长用例通过真实 30 秒定时器从运行中的隔离数据库读取新增记录，并从 UIA 验证更新后的结果。
2. 两个系统验收用例只有在真实 Windows 锁屏/解锁或 Suspend/Resume 流程完成后才可能通过；普通单元测试/模拟 provider 不计入验收。
3. 显示器/DPI 策略接入真实 WPF 定位之后，混合 DPI 位置用例在满足条件的设备上通过；拓扑变化用例按手动设备步骤验证。
4. 默认单元测试和快速 UI smoke tests 不锁屏、不睡眠、不改变显示器/电源设置，也不等待 30 秒。
5. 每个新增测试用例均有 Purpose、Coverage、Target effect；状态文件分别记录自动化结果、环境跳过项和仍未执行的人工验收。
6. Release 构建、101 单元测试和原有 11 个 UI smoke tests 在新增方案实现后仍通过；慢速/硬件验收使用独立过滤器运行并单独报告。

## 9. 非目标

- 在 CI 或无人值守机器上自动锁屏、睡眠、唤醒、解锁或更改显示器配置。
- 通过 mock/stub 的 `SystemEvents` 事件宣称真实系统通知链路通过。
- 测试 hibernate 与 sleep 的识别差异；当前事件源只提供通用 suspend/resume。
- 实现显示器持久化偏好、设置页、托盘或其他 PRD 功能，除非后续实施中发现它们是满足上述定位验收的必要前置条件并先取得确认。
